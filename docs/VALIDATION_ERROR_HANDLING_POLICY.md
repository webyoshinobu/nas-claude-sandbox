# バリデーションルール・エラーハンドリング方針

## 目的

主要なフォーム画面の入力チェック仕様と、フロントエンド・バックエンド双方でのエラー処理方針を明文化する。DB設計(制約)・API設計(openapi.yaml)との整合性を保つための橋渡し役として位置づける。

## 基本方針

- **バリデーションはフロントエンド・バックエンドの両方で行う**(フロントは即時フィードバックのため、バックエンドは信頼できる最終防衛ラインのため。フロントのみのチェックは改ざん可能なため信頼しない)
- **エラーメッセージは日本語で統一**(ポートフォリオの主な閲覧者は日本語話者を想定。英語版READMEとは別に、UI自体は日本語のままでよい)
- **共通のエラー表示コンポーネントを使用**(フォームごとに表示方法がバラつかないようにする)

---

## 1. 会員登録(`POST /api/auth/register`)

| 項目 | ルール | エラーメッセージ例 |
|---|---|---|
| email | 必須、メール形式、255文字以内、重複不可(`users.email`のunique制約と対応) | 「有効なメールアドレスを入力してください」/「このメールアドレスは既に登録されています」 |
| password | 必須、8〜64文字、英数字混在 | 「パスワードは8文字以上で、英字と数字を含めてください」 |
| passwordConfirm | passwordと一致 | 「パスワードが一致しません」 |
| role | 必須、GENERAL/SELLERのいずれか | 「会員種別を選択してください」 |

## 2. ログイン(`POST /api/auth/login`)

| 項目 | ルール | エラーメッセージ例 |
|---|---|---|
| email/password | 認証失敗時、どちらが誤りか特定できるメッセージにしない(セキュリティ上の理由) | 「メールアドレスまたはパスワードが正しくありません」 |
| is_active = false のユーザー | ログイン不可 | 「このアカウントは無効化されています」 |

## 3. アカウント情報編集(`PUT /api/users/me`)

| 項目 | ルール | エラーメッセージ例 |
|---|---|---|
| email | 会員登録時と同様(自分自身の現在値との重複は許可) | 同上 |
| password(変更する場合のみ) | 空欄なら変更しない、入力時は登録時と同じルール | 「パスワードは8文字以上で、英字と数字を含めてください」 |

## 4. 商品登録・編集(`POST/PUT /api/photos`)

| 項目 | ルール | エラーメッセージ例 |
|---|---|---|
| title | 必須、100文字以内 | 「タイトルを入力してください」 |
| price | 必須、1以上の整数(最小通貨単位) | 「価格は1円以上で入力してください」 |
| category | 必須、選択式(自由入力にしない想定) | 「カテゴリを選択してください」 |
| image(新規登録時) | 必須、jpg/png形式、10MB以内 | 「画像ファイル(jpg/png、10MB以内)を選択してください」 |

## 5. カート追加(`POST /api/cart/items`)

| ケース | 挙動 | メッセージ例 |
|---|---|---|
| 既にカートに追加済みの写真 | DBの複合ユニーク制約(`cart_id`, `photo_id`)により追加不可 | 「この写真は既にカートに入っています」 |
| **出品者自身が自分の写真をカートに追加しようとした場合** | **業務ルールとして400エラーでブロック** | **「自分が出品した写真は購入できません」** |

**実装メモ:** `POST /api/cart/items`のサービス層で、`photo.sellerId == currentUser.id`の場合に例外をスローする形で実装する。フロントエンド側でも、自分が出品した写真の詳細ページでは「カートに追加」ボタン自体を非表示にする(またはグレーアウト)ことで、事前にUXレベルでも防止する。

## 6. 決済(`POST /api/orders`, `POST /api/orders/{id}/payment-intent`)

| ケース | 挙動 | メッセージ例 |
|---|---|---|
| カートが空の状態で注文作成 | 400エラー | 「カートに商品がありません」 |
| Stripe決済失敗(カード拒否等) | `orders.status`を`FAILED`に、購入者にエラー内容を表示 | 「決済に失敗しました。カード情報をご確認ください」 |
| Webhookとフロントの状態不一致 | `GET /api/orders/{id}/payment-status`で再確認(既存設計を活用) | 「決済状況を確認中です。しばらくお待ちください」 |

## 7. ダウンロード(`GET /api/downloads/{token}`)

| ケース | HTTPステータス | メッセージ例 |
|---|---|---|
| トークン期限切れ | 410 Gone | 「ダウンロードリンクの有効期限が切れています」 |
| トークン不正・存在しない | 404 Not Found | 「無効なダウンロードリンクです」 |

## エラーハンドリングの全体方針

### バックエンド側

| HTTPステータス | 用途 |
|---|---|
| 400 Bad Request | バリデーションエラー(入力値の形式不正、業務ルール違反など) |
| 401 Unauthorized | 未認証(JWTがない・無効) |
| 403 Forbidden | 認可エラー(権限不足、他人のリソースへのアクセス) |
| 404 Not Found | リソースが存在しない |
| 409 Conflict | 重複エラー(メール重複、カート重複追加など) |
| 410 Gone | 有効期限切れ(ダウンロードトークンなど) |
| 500 Internal Server Error | 想定外のサーバーエラー |

レスポンスボディの形式は統一する(Spring Bootの`@ControllerAdvice`でグローバルにハンドリング):

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": [
      { "field": "email", "message": "有効なメールアドレスを入力してください" }
    ]
  }
}
```

### フロントエンド側

- **フォーム単位のエラー**:各入力項目の直下に赤字でメッセージ表示(項目単位のリアルタイムバリデーション)
- **APIエラー(通信失敗・サーバーエラー)**:画面上部にトースト/バナー表示
- **認証切れ(401)**:自動的にログイン画面へリダイレクト
- **権限エラー(403)**:「アクセス権限がありません」の専用エラーページ、またはトースト表示

## 業務ルール一覧(バリデーションとは別軸の制約)

DB制約・入力形式チェックとは異なる、ビジネスロジックとしての制約。

| ルール | 対象 | 理由 |
|---|---|---|
| 出品者は自分が出品した写真を購入できない | `POST /api/cart/items` | 自作自演の売上計上を防ぐため |
